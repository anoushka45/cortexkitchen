CortexKitchen — Architecture Deep Dive

A complete technical reference for the multi-agent restaurant operations planning system.

LangGraph Qdrant Redis MCP RAG SSE Streaming Critic Loop FastAPI CometAPI

Overview

CortexKitchen is a production-grade multi-agent AI system for restaurant operational planning. Given a scenario — Friday Rush, Holiday Spike, Low-Stock Weekend, or Weekday Lunch — it runs a 12-node LangGraph pipeline that forecasts demand, retrieves memory from Qdrant, runs parallel domain agents, synthesises a consolidated brief, validates it through a critic loop, and streams results node-by-node to the frontend via Server-Sent Events.

Core Design Principle

Every layer degrades gracefully. No single failure crashes the plan. Qdrant down? Agents run without enrichment. Swiggy MCP unavailable? Circuit opens, enrichers return None, planning continues with DB data. LLM critic fails? Sanity checker results still block bad plans. Redis down? Planning runs execute fresh. Each layer is independently fallible.

The system is architected in 8 distinct layers, each solving a different class of problem. You can think of them as concentric rings: orchestration → agent intelligence → validation → memory → caching → external integrations → LLM management → observability. Understanding the layers independently makes the system easier to reason about, test, and extend.

Layer 1 Orchestration Engine

The orchestration layer is the skeleton of the system — it defines what runs, in what order, and under what conditions. CortexKitchen uses LangGraph's StateGraph as its orchestration engine, which gives it parallel execution, conditional branching, and a compiled topology that's verified at startup.

LangGraph StateGraph

LangGraph represents the pipeline as a directed graph of nodes where each node is a Python function that takes the full OrchestratorState (a TypedDict) and returns a partial dict that gets merged back into state. This immutable-update pattern is critical: you can inspect, replay, or unit-test any node in isolation by simply calling it with a constructed state dict.

Why LangGraph over a plain async pipeline?

A plain asyncio.gather() pipeline could handle the parallel fan-out, but LangGraph gives three things you can't easily build yourself: (1) parallel fan-out with guaranteed state merging — reservation, complaint, and inventory run simultaneously and their outputs merge cleanly into a single state object; (2) conditional edges — the critic can branch to replan_orchestrator or final_assembler based on state, not code logic; (3) compiled topology validation — the graph checks for cycles, disconnected nodes, and missing edges at startup, not at runtime when a user is waiting.

Phase1 Sync — The Barrier Pattern

This is one of the most non-obvious design decisions in the codebase and worth understanding deeply. LangGraph uses Pregel-style execution — all nodes at the same "hop count" from the entry point run in the same "superstep." The problem: after the parallel fan-out, reservation and complaint_intelligence were 3 hops from ops_manager, but inventory was also 3 hops. However, in the old topology, inventory → menu_intelligence → aggregator meant inventory was 4 hops from aggregator via menu. This caused aggregator to fire twice — once with partial data at 13ms, then again after menu at 4868ms.

The Bug (now fixed)

Without phase1_sync: aggregator ran at superstep N (when reservation + complaint were done) and again at superstep N+1 (when inventory + menu were done). This produced an early, incomplete plan visible in the UI as "aggregator green before menu." Confirmed via DB query on node_traces: aggregator(13ms) → menu_intelligence(4868ms) → aggregator(26ms) in every run.

The fix is elegant: phase1_sync is a zero-logic passthrough node that all three parallel agents feed into. Now reservation, complaint, and inventory all terminate at phase1_sync (same hop count), and the path from phase1_sync to aggregator goes through menu_intelligence. Every path is the same length → aggregator fires exactly once.

def phase1_sync_node(state):
    """Barrier: equalises hop counts from all parallel paths.
    Ensures aggregator fires exactly once — not twice (Pregel double-fire bug)."""
    return state
Tradeoff

phase1_sync adds ~1ms of overhead per run — the cost of passing state through an extra node. This is negligible. The alternative was restructuring the entire graph topology to manually balance hop counts, which would make the graph harder to read and maintain.

Streaming with astream_events v2

The streaming path uses graph.astream_events(version="v2") instead of the older astream(). The key difference: astream only emits events when a node completes. astream_events emits on_chain_start when a node begins AND on_chain_end when it finishes. This is what enables the UI to show a node as "running" before it's done — the node_start SSE event comes from the on_chain_start hook.

The name field in each event matches the registered node key. A _NODE_SSE_MAP dict translates internal names to frontend-friendly names: "demand_forecast" → "forecast", "complaint_intelligence" → "complaint", etc.

async for event in graph.astream_events(initial_state, config=config, version="v2"):
    etype  = event.get("event", "")   # "on_chain_start" or "on_chain_end"
    ename  = event.get("name", "")    # registered node key
    sse_name = _NODE_SSE_MAP.get(ename)

    if sse_name:
        if etype == "on_chain_start":
            yield {"event": "node_start", "node": sse_name,
                   "hint": _NODE_START_HINTS.get(ename, "")}
        elif etype == "on_chain_end":
            state_update = (event.get("data") or {}).get("output") or {}
            yield {"event": "node_complete", "node": sse_name,
                   "hint": _completion_hint(ename, state_update)}

Layer 2 Agent Intelligence

This layer is where the domain reasoning happens. Each agent has a single well-scoped responsibility and reads from shared state rather than calling shared services directly. The shared_context pattern (established by qdrant_enrichment) is the key coupling mechanism — agents share retrieved memory without needing to know about each other.

Ops Manager

The entry point node. Validates the incoming scenario against known scenario IDs, resolves target_date to a concrete date (defaulting to the next matching service day), and routes. If validation fails, it routes directly to final_assembler with an error state — the rest of the graph never runs. This is the fail-fast pattern: don't burn LLM calls on an invalid request.

Demand Forecast

Queries the orders DB table for historical data matching the scenario's day-of-week and service window. Returns:

  • predicted_orders — the forecast for the target date
  • avg_friday_orders / avg_same_day_orders — historical baseline
  • demand_ratio — predicted / average. This is the key signal. demand_ratio = 1.3 means 30% above average demand.

Every downstream agent uses demand_ratio as the primary scaling factor for their recommendations.

Qdrant Early Enrichment

This is one of the most architecturally significant nodes in the system. It runs a single Qdrant lookup before the parallel fan-out and writes results to state["shared_context"]. All three parallel agents read from this shared context — none of them make their own Qdrant calls.

Why Early Enrichment? (Key Architecture Discussion)

Three agents querying Qdrant independently = 3× calls, 3× latency, inconsistent results. If reservation, complaint, and inventory each ran their own ANN search, they might get different nearest neighbours (non-deterministic ANN) — reservation might retrieve complaint A, while complaint_intelligence retrieves complaint B. The plan would be built on inconsistent context. Early enrichment guarantees: one query (30–50ms), deterministic shared context, zero per-agent retrieval overhead.

The enrichment node retrieves three types of context:

  • Complaints (top-5, cosine similarity) — past guest complaint text, used by complaint_intelligence for RAG
  • SOPs (top-3) — Standard Operating Procedures relevant to the scenario query
  • Past plans (top-3, recency-decayed) — approved planning insights from previous runs for this scenario and org

Parallel Domain Agents

Three agents run simultaneously after qdrant_enrichment — this is the parallel fan-out. They all read from shared_context but otherwise operate independently.

AgentPrimary InputKey Output
reservationReservation DB + occupancy dataoccupancy_pct, waitlist count, booking conflicts
complaint_intelligenceshared_context complaints + SOPsRisk summary, complaint categories, SOP recommendations
inventoryInventory DB + demand_ratioShortage alerts, overstock alerts, restock quantities (capped at 3×)

Inventory 3× Restock Cap

The inventory agent calculates restock quantities as needed = (predicted_covers * per_cover_usage) - current_stock. Early versions could produce absurd restock recommendations (e.g. "order 500kg of chicken for 180 covers"). A deterministic cap was added: restock_qty = min(calculated_qty, current_stock * 3). You can't recommend restocking more than 3× what you currently hold. This cap is also checked by the EvaluationSanityChecker and overridden if violated.

Menu Intelligence

Runs sequentially after phase1_sync. This is an intentional correctness choice, not a performance concession. If menu_intelligence ran in parallel with inventory, it would make recommendations ("push the pasta special") without knowing whether the pasta ingredients are actually in stock. By running after inventory data is in state, it can produce constraint-aware suggestions ("deprioritise the sea bass — critical shortage flagged").

Tradeoff: Correctness vs Latency

Sequential menu adds ~1–2s to total run time vs running it in parallel. The alternative (parallel menu + post-hoc inventory constraint injection) would require the aggregator to detect and correct contradictions between menu and inventory suggestions — messy, error-prone, and hard to explain. Sequential is the right call.

Aggregator

Takes all five agent outputs (forecast, reservation, complaint, inventory, menu) and synthesises them into a unified operational brief. The aggregator doesn't just concatenate — it actively runs contradiction detection via _detect_contradictions(): pairwise checks across agent outputs for logical conflicts. Example: reservation says "low occupancy expected" while forecast says "1.4× demand ratio." This contradiction is flagged and passed to the critic as part of the synthesis context.

Layer 3 Validation & Critic

Validation is a two-stage process: fast deterministic checks first, then a slower LLM-based evaluation. The deterministic layer catches hard constraint violations that an LLM might reason around. The LLM layer catches quality and coherence issues that no deterministic rule can express. Running them in the right order is what makes the system reliable.

Why Two Validation Layers?

LLM critics are good at reasoning but can be convinced. Give an LLM critic a plan that says "serve 90 covers" when capacity is 70, and depending on the prompt framing, it might approve it ("the kitchen seems efficient"). A deterministic checker will always flag predicted_covers > org_capacity * 1.05. Conversely, a deterministic checker can't evaluate whether the plan is "actionable" or "well-evidenced" — that requires reasoning. Both layers are necessary; neither is sufficient alone.

Deterministic Sanity Layer

EvaluationSanityChecker runs BEFORE the LLM critic on every planning cycle. It checks:

  • Capacity violation: predicted_covers > org_capacity * 1.05 → flag as critical
  • Restock cap: any restock recommendation exceeding 3× current stock → cap and flag
  • Guest language: non-English text in guest name fields → sanitise
  • Assumption staleness: agent outputs that contradict each other → stale_assumptions list

The checker returns a stale_assumptions list. Critical assumptions can override the LLM's verdict — even if the LLM says approved, a critical sanity violation bumps the verdict to revision. This is the "sanity override" pattern: deterministic rules have veto power.

LLM Critic — 5 Dimensions

The LLM critic evaluates the synthesised plan across five independent dimensions. Each dimension gets a sub-score; the final score is a weighted aggregate.

Safety Feasibility Evidence Actionability Clarity
DimensionWhat it checks
SafetyDoes anything violate capacity limits, food safety constraints, or guest safety policies?
FeasibilityCan the kitchen actually execute this plan given current staff levels and stock?
EvidenceAre recommendations grounded in the data the agents actually returned — or are they hallucinated?
ActionabilityAre the actions specific enough for ops staff to follow without further interpretation?
ClarityIs the plan unambiguous? Could a different ops manager interpret it differently?

The critic returns: verdict, score (0.0–1.0), and notes (human-readable explanation of the judgement). The notes become part of actionable_feedback injected into the replan cycle.

Cross-Agent Assumption Diffing

One of the most sophisticated features of the system. The aggregator extracts "assumptions" from each agent output — structured statements about what the agent assumed to be true when making its recommendation. For example:

  • Reservation agent: "assumes 65% occupancy based on confirmed bookings"
  • Demand forecast: "assumes 180 predicted orders based on historical Friday data"

_diff_assumptions() in EvaluationSanityChecker diffs these pairwise. If demand says 1.4× but reservation says low occupancy, that's a contradiction — flagged as a stale_assumption and surfaced to the critic. This surfaces contradictions automatically without needing hardcoded pairwise rules for every possible agent pair.

Replanning Loop

When the critic returns revision, the graph routes to replan_orchestrator instead of final_assembler. The replan cycle:

  1. replan_orchestrator reads revision_reasons and actionable_feedback from state
  2. Injects them into replan_context — a new state field
  3. aggregator re-runs. This time it reads replan_context and uses it to regenerate the synthesis with corrective guidance
  4. critic re-evaluates the new synthesis
  5. If still revision and replan_count < 2, loop continues. Otherwise exits via final_assembler
Why Max 2 Retries?

Each replan cycle costs ~1.2–1.8s in LLM calls (aggregator + critic). At max 2 retries, worst-case adds ~3.6s. At 3 retries, you've more than doubled total latency for diminishing returns — the critic's feedback rarely changes fundamentally after the first replan. Two gives a genuine second chance without death-by-retry. The replan_count is tracked in state and visible in the UI as a "Replan" banner.

Critic Threshold Configuration

The critic_threshold is stored in organizations.settings as a JSONB float (default 0.7). This is a per-org configuration — different restaurant types can have different acceptance bars.

Restaurant TypeSuggested ThresholdReasoning
Fine dining, high-risk events0.85Low tolerance for plan quality issues; reputation cost of errors is high
Standard full-service0.7 (default)Balanced quality/speed tradeoff
Quick-service, fast-casual0.60–0.65Speed matters more; plans are simpler; lower consequence of minor gaps

Code path: org_settings.get("critic_threshold", 0.7) → passed to stream_planning_scenario() → written to initial_state["critic_threshold"] → read by critic_node from state at evaluation time.

Layer 4 Memory & Retrieval

Memory in CortexKitchen is organised into three tiers: operational memory (complaints + SOPs from Qdrant), long-term planning memory (approved run insights with recency decay), and conversational memory (cross-session chat summaries). Each tier serves a different time horizon and use case.

MemoryService — Complaints + SOPs

infrastructure/vector/memory_service.py. Two Qdrant collections:

  • complaint_memory: embedded guest complaint text, filtered by org_id. Retrieved via cosine ANN search, top-5 by default.
  • sop_memory: embedded SOP rules and operational guidelines. Retrieved via cosine ANN search, top-3 by default.

Both collections use Gemini's models/gemini-embedding-001 (via EmbeddingService) for embedding. All queries use Qdrant's FieldCondition payload filter on org_id — no org can retrieve another org's data.

PlanningMemoryService — Long-Term Planning Intelligence

infrastructure/vector/planning_memory.py. A new Qdrant collection: planning_memory. After each approved planning run, the system embeds and stores a rich insight text derived from the run's output. What gets embedded:

"scenario:friday_rush | demand_ratio:1.38 predicted:182 | shortages:chicken,basil | occupancy:78% | verdict:approved score:0.84 | menu:deprioritise sea bass, push pasta specials"

This condition-rich text means future ANN retrievals match on what the situation was, not just the scenario name. A high-demand Friday with chicken shortage retrieves past plans that had the same conditions — not just all past Friday Rush plans.

Why only APPROVED runs?

Storing rejected or revision plans would pollute memory with bad patterns. If a future enrichment retrieved "what didn't work last time" as positive context, agents would be primed to make the same mistakes. Only approved plans represent validated operational intelligence worth learning from. The planning_memory.store() call is gated on verdict == "approved" in both the sync and stream paths.

Recency Decay

Raw ANN similarity scores are multiplied by a recency decay factor before re-ranking:

decayed_score = raw_similarity * 2^(-age_days / HALF_LIFE_DAYS)
# HALF_LIFE_DAYS = 14
Age of MemoryDecay FactorEffect on Score
1 day0.95Near-full weight
7 days0.71Slightly reduced
14 days (half-life)0.50Half weight
28 days0.25Quarter weight
> 90 days0 (excluded)Hard cutoff
Why Decay Instead of TTL?

TTL is binary — memory is fully relevant until it expires, then completely gone. A 3-week-old plan might still be marginally useful (same seasonal pattern, same staffing constraints), but a 90-day TTL would discard it at day 91. Decay is continuous — relevance fades gracefully. The 90-day hard cutoff handles the case where a plan is so old it refers to a fundamentally different operational context (new menu, new staff, seasonal change).

The retrieve path over-fetches (top_k × 2 results from Qdrant), applies decay to all results, re-sorts by decayed score, and returns the true top_k. This avoids the case where the #1 ANN result is 6 weeks old and scores worse than the #3 result from 2 days ago after decay.

SessionMemoryService — Cross-Session Chat

infrastructure/vector/session_memory.py. Qdrant collection: chat_sessions. At the start of each chat session, retrieves similar past session summaries (semantic similarity, top-3) and injects them into the chatbot's system prompt. This gives the chatbot continuity across conversations without replaying full history.

build_summary_from_messages() extracts key topics (inventory, demand, menu, reservations, critic evaluation) via keyword matching — no LLM call needed. This is intentional: generating a session summary with an LLM adds latency and cost at session end. Lightweight local processing is enough for the topical summary needed for next-session context injection.

Layer 5 Caching Strategy

CortexKitchen has three distinct cache layers, each serving a different purpose. The key insight: caching is not one-size-fits-all. Exact-match caching and semantic caching solve different problems — don't use one when you need the other.

CacheBackendKey / MatchThresholdTTLWritten when
Redis exact-matchRedisplan:{org_id}:{scenario}:{date}Exact1 hourCritic = approved only

Redis Exact-Match Cache

infrastructure/cache/plan_cache.py. First check on every /planning/run and /planning/stream call. Key: plan:{org_id}:{scenario}:{date}. If found: return immediately — zero LLM calls, zero agent runs. TTL: 1 hour.

Why only write on approved?

Writing a rejected or revision plan to the Redis cache would return that plan to the next caller — they'd get a "planning complete" response that's actually a failed plan. The Redis cache is the fast-path return; it should only serve validated, usable plans. Cache-hit responses still create a planning_run DB record (with cache_hit: true) so the run appears in history.

Semantic Plan Cache

infrastructure/cache/semantic_cache.py → SemanticPlanCache. Qdrant-backed. Embeds the text "org:{id} scenario:{scenario} date:{date}" and searches for past runs with cosine similarity ≥ 0.92. The semantic match catches requests that are functionally equivalent even if the exact date differs — "friday_rush 2026-06-28" and "friday_rush 2026-07-05" should be highly similar (both Friday Rush scenarios).

Why 0.92 threshold?

0.85 would over-match — a Friday Rush query might retrieve a Weekday Lunch result. 0.97 would under-match — nearly identical requests wouldn't cache. 0.92 is the empirically safe zone where the same scenario on different dates matches, but different scenarios don't. The embedding model (Gemini embedding-001) places scenario names far enough apart in vector space that 0.92 is the right boundary.

Semantic Chat Cache

SemanticChatCache in the same file. Embeds the user's question and checks for similar past Q&A pairs. If "What was last Friday's occupancy?" was asked and answered, a semantically similar follow-up like "How full were we last week Friday?" hits the cache. TTL: 24 hours.

Cache Hit SSE Path

When the streaming endpoint has a Redis cache hit, it emits all node_complete events instantly (no node_start events — the nodes didn't run), then the complete event. The UI shows all nodes lighting up simultaneously — a visually distinct signal that this was served from cache. The cached: true flag on each node_complete event lets the frontend differentiate if needed.

Layer 6 MCP Integration

CortexKitchen operates in both directions of the MCP ecosystem simultaneously: it exposes itself as an MCP server (callable by Claude Desktop, other agents, or any MCP client) and it acts as an MCP client calling Swiggy's external MCP endpoints. This dual-role architecture is what makes CortexKitchen genuinely agentic — it can be orchestrated by others and it can orchestrate external services.

CortexKitchen as an MCP Server

apps/api/mcp_server.py. A stdio MCP server exposing two tools:

ToolArgsReturns
run_planning_scenarioscenario (required), target_date?, restaurant_id?Formatted markdown: critic verdict, recommendations per agent, cost, duration
get_run_historylimit?, scenario?, verdict?Recent planning runs with scenario, date, verdict, score
Why 2 tools, not 12?

Exposing run_demand_forecast or run_critic as individual MCP tools would be wrong — they're internal implementation details, meaningless in isolation. An external agent calling run_demand_forecast would have no way to know it needs to also call qdrant_enrichment then reservation then... The tool granularity should match the intent granularity of the calling agent. "Plan for Friday Rush" is one intent — one tool. This is the core principle: MCP tools are capabilities, not functions.

Swiggy as MCP Client

infrastructure/swiggy/client.py → SwiggyMCPClient. Calls three Swiggy JSON-RPC 2.0 MCP endpoints:

  • https://mcp.swiggy.com/food — food orders, demand signals, competitor data
  • https://mcp.swiggy.com/im — Instamart procurement and inventory
  • https://mcp.swiggy.com/dineout — reservation data from Swiggy Dineout

The primary contract of SwiggyMCPClient: never raises, always returns None on failure. 401 → log + None. 5xx → retry once after 1s → if still 5xx → None. Network error → None. Bad response format → None. This is what makes the Swiggy layer a graceful enhancement rather than a hard dependency.

BaseConnector ABC

infrastructure/swiggy/base_connector.py. Every external platform connector must implement two methods:

class BaseConnector(ABC):
    @abstractmethod
    async def sync(self) -> dict:
        """Nightly job. Pull historical data. Write to DB."""

    @abstractmethod
    async def enrich(self, context: dict) -> dict | None:
        """At planning time. Fetch live signals. Do NOT write to DB.
        MUST return None on any failure."""

The enrich()→None contract is enforced at the ABC level. Any connector that raises from enrich() violates the contract — the caller has no try/except. This design means you can add Zomato, EazyDiner, or Square POS as connectors and the planning pipeline will safely degrade if any of them fail.

Circuit Breaker

infrastructure/swiggy/circuit_breaker.py. Redis-backed, per-endpoint. Protects the planning pipeline from repeatedly hammering a degraded Swiggy endpoint.

✓ CLOSED (normal)

Calls pass through. Failure counter tracked in Redis with 5-minute TTL. Counter auto-resets if no failures occur within the window.

✗ OPEN (degraded)

3 failures in 5 minutes triggered this. All calls return None immediately — no HTTP call attempted. Auto-resets after 30 minutes via Redis TTL.

# On each call_tool() invocation:
if await is_open("swiggy", server_tag):
    self._traces.append({..., "status": "circuit_open"})
    return None   # short-circuit, no HTTP call

# ...make HTTP call...
result = await self._post(...)

if result is None:
    await record_failure("swiggy", server_tag)
    # If failures >= 3: SETEX circuit:open:swiggy:{tag} 1800 "1"
else:
    await record_success("swiggy", server_tag)
    # DEL circuit:fail:swiggy:{tag}  ← faster recovery
Why TTL-based reset, not half-open state?

Classic circuit breakers have CLOSED → OPEN → HALF-OPEN (single probe) → CLOSED. The half-open state lets you test the connection before fully reopening. TTL-based skips the probe — after 30 min, the circuit closes automatically and the next real call acts as the implicit probe. For a restaurant planning system where failures are typically transient (Swiggy briefly down, token expired), a 30-minute wait is appropriate and the simplicity of TTL-based reset is worth more than the precision of a half-open probe.

infrastructure/swiggy/provider_registry.py. Maps planning capabilities to prioritised lists of providers. No DB migration needed — reads the existing connectors table to determine which providers are active for an org.

Capability Discovery & Governance — The Honest Picture

Current capability discovery is static: each enricher hardcodes which Swiggy tools it calls. There are no runtime tools/list calls at startup to discover available capabilities dynamically. Swiggy's llms.txt is consulted manually when adding new tools.

The Open Problem

When two providers can fulfil the same capability (e.g. Swiggy Dineout and EazyDiner both provide reservation data), the Provider Registry solves the routing problem — which one wins for this org. It doesn't solve the capability-matching problem for novel tools: if Swiggy adds a new "customer_sentiment" tool tomorrow, no code currently knows to use it for complaint enrichment. Full capability discovery would require an LLM to reason about tool schemas and match them to enrichment needs — a non-trivial agentic problem in itself. The governance gap is real and acknowledged, not papered over.

GET /health/circuits returns live circuit state for all 3 Swiggy endpoints: {state, recent_failures, resets_in_seconds} — the start of a governance visibility layer.

Layer 7 LLM Provider Architecture

CortexKitchen doesn't hardcode a single LLM provider. The provider layer is designed for flexibility — switch between Groq, CometAPI, and Gemini via env var, with automatic fallback if the primary fails. In CometAPI mode, different nodes get different model tiers based on their reasoning requirements.

FallbackLLMProvider

infrastructure/llm/factory.py → FallbackLLMProvider. Wraps a primary and optional fallback provider. Exposes the same complete() and complete_json() interface as the underlying providers. On any exception from the primary, silently retries with the fallback. Tracks last_provider_used and last_fallback_used for observability logging. drain_usage() collects token usage records from both primary and fallback for cost attribution.

async def complete(self, prompt, system_prompt=None):
    try:
        result = await self.primary.complete(prompt, system_prompt)
        self.last_provider_used = self.primary.provider_name
        return result
    except Exception:
        # Log warning with provider names, then:
        result = await self.fallback.complete(prompt, system_prompt)
        self.last_fallback_used = True
        return result

Tiered Routing (CometAPI mode)

When LLM_PROVIDER=comet and COMET_TIERED=true, create_tiered_llm_providers() builds a registry keyed by tier name. Nodes read their tier from state and use the matching provider:

TierDefault ModelFallbackUsed by
fastdeepseek-v4-flash—Demand forecast, reservation, inventory
balancedgemini-3.5-flashfastComplaint intelligence, menu
strongclaude-sonnet-4-6balancedAggregator, critic
defaultCometAPI default—Nodes without explicit tier
Why Tiered Routing?

Not all nodes need a frontier model. Demand forecast is a straightforward calculation — deepseek-v4-flash is fast and cheap and handles it fine. The critic evaluating a plan across 5 dimensions and the aggregator synthesising 5 agent outputs into a coherent brief genuinely need a stronger model to avoid surface-level, low-quality outputs. Tiered routing routes model capability where it's actually needed, cutting cost ~40–60% vs running everything on the strong model.

Chatbot LLM Factory

The chatbot uses the OpenAI-compatible chat.completions.create() interface with streaming and ReAct tool calls. Both Groq and CometAPI expose this interface, so the factory simply returns the right async client based on LLM_PROVIDER:

def _get_chat_client(settings):
    provider = settings.llm_provider.strip().lower()
    if provider == "groq":
        from groq import AsyncGroq
        return AsyncGroq(api_key=settings.groq_api_key), "llama-3.3-70b-versatile"

    # comet / gemini / anything else → CometAPI OpenAI-compat endpoint
    from openai import AsyncOpenAI
    return (
        AsyncOpenAI(api_key=settings.cometapi_key,
                    base_url="https://api.cometapi.com/v1"),
        settings.cometapi_model_fast,
    )

The ReAct tool loop, streaming path, and semantic cache logic all work identically regardless of which client is returned — the interface is identical.

Groq vs CometAPI for Chat

Groq's LPU hardware is optimised for fast token generation — better for the chatbot's interactive latency requirement where every 100ms matters. CometAPI with its access to 500+ models (including Claude and Gemini) is better for the planning pipeline where quality matters more than first-token latency. The factory makes this a one-env-var decision, not a code change.

Layer 8 Observability

Observability in CortexKitchen operates at multiple levels: per-node cost and timing attribution in every planning response, Sentry error tracking for production incidents, and live health endpoints for both infrastructure dependencies and external provider circuit states.

Per-Node Cost Attribution

Every planning response includes a meta.node_traces array. Each trace record contains:

{
  "node_name":    "critic",
  "duration_ms":  1247.3,
  "llm_usage": [
    {"model": "claude-sonnet-4-6",
     "prompt_tokens": 2841, "completion_tokens": 312,
     "cost_usd": 0.003212}
  ]

The final meta block aggregates across all nodes: total_duration_ms, total_tokens, total_cost_usd. All of this is stored in the planning_runs DB table via RunService — every run is a permanent record you can query to understand which nodes are expensive, which are slow, and how cost trends over time.

Sentry Integration

Node errors are captured by Sentry with structured context: org_id, scenario, node_name. LangGraph doesn't surface node-level errors through the graph result — a node error is swallowed and appears as a missing output. Without Sentry, you'd debug silent failures from missing state keys. With Sentry, you get a full traceback with context at the point of failure.

Real-Time Streaming UI

The frontend receives planning progress via Server-Sent Events and renders a live 4-state node pipeline. Each node transitions through idle → running → done (or skipped) as events arrive. Hint text shows what the node is doing while running, then what it found when done.

node_complete
{node: str, hint: str, cached?: bool} — emitted when a node finishes. hint is a brief summary of what it found.

node_start + node_complete Hints

Two separate hint sources in graph.py:

  • _NODE_START_HINTS: Static dict, keyed by node name. Emitted immediately on on_chain_start. Example: "qdrant_enrichment" → "Searching Qdrant memory for relevant SOPs and past incidents…"
  • _completion_hint(node_name, state_update): Extracts structured info from the node's state update output. Examples:
    • demand_forecast → "gradient-boost model: 182 predicted orders"
    • qdrant_enrichment → "Memory loaded: 5 complaints, 3 SOPs, 2 past plans"
    • critic → "approved (0.82) — plan is feasible and well-evidenced"
Fixed Bug: Hints Were Being Dropped

The original planning.py SSE route only forwarded node_complete events and silently dropped all node_start events. Hints were stripped from node_complete too. This is why the loading pipeline only ever showed "Waiting" or "Done" — the running state never triggered. Fixed by forwarding both event types with their hints.

⚠ Tradeoffs & Limitations

Every architectural decision has a cost. This section documents the known tradeoffs, limitations, and gaps honestly — both the intentional ones (where the tradeoff was made consciously) and the genuine gaps (where work is pending or not yet done).

1
Menu Intelligence runs sequentially (~1–2s added latency)

Menu depends on inventory data to make constraint-aware suggestions. Running it in parallel with inventory would produce menu recommendations that contradict available stock. Sequential is a correctness choice, not a performance failure. The tradeoff: ~1–2s added to total pipeline time.

2
Max 2 replan cycles (latency vs quality tradeoff)

Each replan cycle costs ~1.2–1.8s (aggregator + critic LLM calls). Two cycles adds at most ~3.6s. Three cycles would add ~5.4s for diminishing returns — the critic's feedback rarely changes fundamentally after the first replan. The cap exists to bound worst-case latency, not because the plan is good enough after 2 retries.

3
✓ FIXED SemanticPlanCache stores all runs, not just approved

This was a minor bug: a rejected plan could be returned as a cache hit to a future caller. The Redis exact-match cache is write-gated on approved only, but the Qdrant semantic cache was writing on every run.

Resolution: SemanticPlanCache.set() is now only called when verdict == "approved". The write in graph.py is explicitly gated: if semantic_cache and org_id and verdict == "approved" and not simulation_mode. Rejected plans can no longer pollute the semantic cache or be returned as hits to future callers.

4
✓ FIXED Semantic cache embedding is basic (scenario + date text only)

At retrieval time the conditions (demand ratio, shortage items, occupancy) aren't yet known — those are computed during the run — so the query embedding must stay lightweight. The storage embedding, however, can be much richer.

Resolution: Asymmetric embedding strategy implemented in SemanticPlanCache. _query_text() stays lightweight: "org:{id} scenario:{scenario} date:{date}". New static method _storage_text() builds a richer string including demand_ratio, occupancy%, shortages:[items], and verdict — e.g. "org:1 scenario:friday_rush date:2026-06-27 demand_ratio:1.42 occupancy:88% shortages:chicken,cream verdict:approved". Storage is now condition-aware; queries still match at scenario-level but stored vectors are semantically richer so future near-miss retrieval is more accurate. graph.py extracts these conditions from the completed run and passes them via the new optional conditions parameter on SemanticPlanCache.set().

5
Swiggy enrichers are stubs — enrich() raises NotImplementedError

SwiggyConnector.enrich() currently raises NotImplementedError. The planning pipeline runs entirely on DB data. Swiggy MCP is integrated at the infrastructure level (client, circuit breaker, connector ABC) but the enrichers (CompetitorEnricher, OccupancyEnricher, ProcurementEnricher) are pending implementation. Live Swiggy enrichment during planning is not yet wired.

6
✓ FIXED Chatbot has no within-session memory (only cross-session)

SessionMemoryService provides cross-session context via Qdrant summaries. Previously, within a single session the chatbot only kept the last 6 turns verbatim — early context was silently dropped.

Resolution: Within-session context compression implemented in chat_service.py. Constant _RECENT_WINDOW = 8. When len(history) > 8, older turns are compressed via SessionMemoryService.build_summary_from_messages(older, question) — a lightweight rule-based summariser (no extra LLM call). The summary is injected as an assistant turn: "[Earlier in this session: ...]", followed by the 8 most recent turns verbatim. The LLM therefore always has: cross-session context (Qdrant), a compressed summary of earlier in this conversation, and the last 8 turns in full. Long conversations no longer lose early context.

7
Circuit breaker uses TTL-based reset (no half-open probe)

After the 30-minute open period, the circuit closes automatically and the next real call acts as an implicit probe. If Swiggy is still down, that call will fail and re-open the circuit. Classic half-open state would send a single probe before reopening fully. The TTL approach is simpler but means one call will fail after every 30-minute recovery attempt if the provider is still degraded.

8
✓ FIXED Provider registry reads connector health at query time (not real-time)

The connectors table's sync_status is written by the nightly sync job. Mid-day degradation was invisible to the registry until the next nightly run.

Resolution: ProviderRegistry.get_provider_async() now performs a dual health check. For each candidate provider: (1) DB check — sync_status in {"success", "syncing"} (nightly, coarse-grained); (2) Circuit breaker check — await circuit_breaker.is_open(provider, endpoint) (real-time Redis, sub-second). A provider only passes routing if it passes both. If Swiggy's food endpoint has had 3 failures in the last 5 minutes, its circuit is open and the registry skips it — falling through to the next priority provider (e.g. Zomato for order_history). The sync version (get_provider) retains DB-only behaviour for backward-compat in sync code paths.

9
MCP capability discovery is static

No runtime tools/list calls are made at startup. Each enricher hardcodes which Swiggy tools it calls. If Swiggy adds a new relevant tool, code must be updated manually. Full runtime discovery would require an LLM to reason about tool schemas and match them to enrichment needs — a separate agent-level problem.

10
phase1_sync adds ~1ms per run

The barrier node is a passthrough — it does nothing except allow LangGraph's Pregel superstep logic to equalise hop counts. The 1ms overhead is negligible. The alternative was manually counting hops and restructuring the graph topology, which would make the graph harder to understand and modify.

Why per-org settings in JSONB?

A fine-dining restaurant and a quick-service restaurant have fundamentally different operational constraints. Capacity, peak hours, and quality thresholds should be tenant-configurable without code changes. JSONB in Postgres is the right fit: schema-flexible (different orgs can have different keys), queryable with Postgres operators, and no migration required to add new settings fields.
