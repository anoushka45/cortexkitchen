Chapter 00

The Big Picture

What CortexKitchen is becoming and why Swiggy MCP changes everything.

Before Swiggy, CortexKitchen was a synthetic-data planning tool. You'd trigger a scenario, 9 LangGraph agents would analyze fake orders and seed data, the critic would score the plan, and you'd get a recommendation. Useful as a demo. Not useful as a real product.

With Swiggy MCP, CortexKitchen becomes a Swiggy-native restaurant operating system. Every data point the agents reason about comes from real Swiggy platform data — your actual orders, delivery times, competitor prices, how full nearby restaurants are tonight.

🎯
The one-liner: "The operating brain for a Swiggy-native restaurant — knows your business, knows your market, acts on your behalf using Swiggy's own data."

The three data layers we're building

LAYER 0 — PostgreSQL (permanent, always authoritative) orders table ← real Swiggy delivery orders (synced nightly) ✅ working feedback table ← real delivery timing, late/on-time ✅ working reservations table ← Dineout bookings ⏳ skeleton (P6-S16) connectors table ← per-org OAuth tokens, sync status LAYER 1 — Redis (30 min TTL, live market intelligence) competitor_pricing ← what rivals charge right now 📋 P6-S07 (next) area_occupancy ← how full nearby restaurants are tonight 📋 P6-S08 (next) ingredient_market ← Instamart prices for our shortage items 📋 P6-S09 (next) LAYER 2 — Action surface (with owner approval gates) Instamart cart → checkout ← one-tap procurement after approval 📋 P6-S15 Dineout book_table ← open more slots when surge predicted 📋 P6-S16

Right now we have Layer 0 working. Layers 1 and 2 are what the next 10 weeks build.

Chapter 02

The Protocol — How JSON-RPC 2.0 Works

MCP uses JSON-RPC 2.0. Here's exactly what every request and response looks like.

MCP (Model Context Protocol) was invented by Anthropic as a standard way for AI agents to call external tools. Swiggy adopted it. The underlying protocol is JSON-RPC 2.0 — a simple standard where every call looks the same, just the tool name and arguments change.

Every request follows this exact shape

Any Swiggy tool call — HTTP requesthttp
POST https://mcp.swiggy.com/food
Authorization: Bearer YOUR_5_DAY_TOKEN
Content-Type: application/json
Accept: application/json, text/event-stream   # REQUIRED — server returns 406 without this

{
  "jsonrpc": "2.0",
  "method": "tools/call",       # always "tools/call" — never changes
  "params": {
    "name": "get_food_orders",  # THIS changes per tool
    "arguments": {           # THIS changes per tool
      "addressId": "addr_01",
      "orderCount": 20
    }
  },
  "id": 1
}

The response — what actually comes back (discovered via live test)

🔴
Critical discovery: Swiggy's documentation showed {"success": true, "data": {...}} as the response format. The real server returns JSON-RPC 2.0 format. We discovered this when we got our actual OAuth token in P6-S06. All parsing code has been updated.
Actual Swiggy response — successjson
{
  "result": {
    "content": [
      { "type": "text", "text": "Human-readable summary..." }
    ],
    "structuredContent": {       # <-- THIS IS THE DATA WE USE
      "orders": [...]
    }
  },
  "jsonrpc": "2.0",
  "id": 1
}

# Error response:
{
  "error": { "code": -32601, "message": "Tool not found" },
  "jsonrpc": "2.0",
  "id": 1
}

Our call_tool() method extracts result["structuredContent"] and returns it directly. You never see the envelope in your sync/enricher code — you just get the data dict.

What your sync code sees: raw = await client.call_tool("get_food_orders", {...}) What raw actually contains: { "orders": [...] } ← structuredContent, unwrapped What the wire looks like: { "result": { "structuredContent": { "orders": [...] } } }
Chapter 03

OAuth — Getting the Token

OAuth 2.1 with PKCE — what it is, why it's needed, and what our script does step by step.

Before calling any tool, you need a Bearer token that proves you're an authorised Swiggy user. Swiggy uses OAuth 2.1 with PKCE (Proof Key for Code Exchange) — a secure auth flow designed for apps that can't safely store a client secret.

PKCE works by generating a random secret, hashing it, and using the hash as a "proof" — Swiggy never sees the original secret until the final token exchange, making it impossible to intercept.

Step 1 — PKCE setup (scripts/get_swiggy_token.py) code_verifier = secrets.token_urlsafe(32) # random secret, never sent until step 6 code_challenge = base64url(sha256(code_verifier)) # hash of it — safe to send publicly Step 2 — Start local callback server HTTPServer on localhost:8080 # waits for Swiggy to redirect back Background thread — doesn't block Step 3 — Open browser https://mcp.swiggy.com/auth/authorize ?response_type=code &client_id=swiggy-mcp &redirect_uri=http://localhost:8080/callback &code_challenge=HASHED_SECRET &code_challenge_method=S256 &scope=mcp:tools Step 4 — You log in (phone + OTP in browser) Swiggy shows its login page You enter your phone number + OTP Step 5 — Swiggy redirects back GET http://localhost:8080/callback?code=AUTH_CODE&state=cortexkitchen-local Our server catches this, stores code, shuts down Step 6 — Exchange code for token POST https://mcp.swiggy.com/auth/token { grant_type, code, code_verifier, client_id, redirect_uri } Step 7 — Save to .env SWIGGY_ACCESS_TOKEN = eyJ... (expires in 5 days) SWIGGY_ADDRESS_ID = cjpfcd75ofl5oefqs8mg

The script lives at 📄scripts/get_swiggy_token.py. Run it with python scripts/get_swiggy_token.py — browser opens, you OTP, done. Token and address ID land in ⚙️apps/api/.env automatically.

✅
You have a confirmed working address ID: cjpfcd75ofl5oefqs8mg. This is required for all Food and Instamart tool calls. Dineout uses a different location system (get_saved_locations).

Token lifecycle

  • Expires: 5 days (432,000 seconds)
  • No refresh tokens in Builders Club v1 — must re-run the full OAuth flow on expiry
  • 401 response = token expired → re-run get_swiggy_token.py
  • 419 response = session revoked → full re-auth
  • In production: each restaurant owner authenticates their own Swiggy account. Tokens stored per org_id in the connectors table (encrypted). Dev uses .env for simplicity.

Chapter 07

SwiggyMCPClient — The Foundation

📄apps/api/app/infrastructure/swiggy/client.py ✅ Done

This is the lowest layer — every Swiggy tool call in the entire system goes through this class. Its entire purpose is to be a safe, observable HTTP wrapper around the Swiggy MCP API.

The primary contract: it never raises. Every failure returns None. Your sync services and enrichers don't need try/except — if the client returns None, they skip gracefully.

The class at a glance

client.py — key partspython
class SwiggyMCPClient:
    def __init__(self) -> None:
        self._traces: list[dict] = []   # accumulates call traces for observability

    def is_available(self) -> bool:
        return bool(get_settings().swiggy_access_token)  # quick check before calling anything

    async def call_tool(self, endpoint, tool_name, arguments) -> dict | None:
        # 1. Check circuit breaker (is this endpoint healthy?)
        if await is_open(_PROVIDER, server_tag):
            return None                              # short-circuit, no HTTP call

        # 2. Build headers — token + Accept (REQUIRED)
        headers = {
            "Authorization": f"Bearer {token}",
            "Content-Type": "application/json",
            "Accept": "application/json, text/event-stream",
        }

        # 3. POST the JSON-RPC payload, handle response
        result = await self._post(endpoint, payload, headers, ...)

        # 4. Update circuit breaker based on result
        if result is None: await record_failure(...)
        else:             await record_success(...)

        return result  # structuredContent dict, or None on any failure

    async def _post(self, ...):
        # 401 → log "token expired", return None
        # 406 → log "Accept header missing", return None
        # 5xx → retry once after 1s, then return None
        # JSON-RPC error key → log, return None
        # No "result" key → log, return None
        # result.structuredContent → return it  ← primary path
        # result.content[0].text → return {"text": "..."} ← fallback

    def drain_traces(self) -> list[dict]:
        return self._traces  # call at end of connector run to collect observability data

What a trace looks like

Every call appends one trace entry regardless of outcome. This powers the /health/circuits endpoint.

Trace entry shapejson
{
  "provider":    "swiggy",
  "endpoint":    "food",
  "tool":        "get_food_orders",
  "status":      "ok",   // "ok" | "circuit_open" | "auth_error" | "http_406" | "tool_error" | "exception"
  "duration_ms": 234.1,
  "attempt":     1
}

Chapter 08

Circuit Breaker

📄apps/api/app/infrastructure/swiggy/circuit_breaker.py ✅ Done

Swiggy goes down sometimes. Without a circuit breaker, every planning run during an outage would hang for 30 seconds per tool call, accumulating failures. The circuit breaker prevents this by stopping calls to a degraded endpoint automatically.

CLOSED (normal) Every call goes through. Failures counted in Redis. If failures >= 3 within 5 minutes: ↓ OPEN (blocked) All calls short-circuit to None immediately. No HTTP requests. Circuit:open:swiggy:{endpoint} key set in Redis with 30min TTL. Auto-resets when TTL expires. On success: failure counter cleared → faster recovery. FAIL-OPEN (Redis down) If Redis is unavailable, is_open() returns False. Calls go through anyway. Safety > correctness.

Redis keys

KeyValueTTL
circuit:fail:swiggy:foodfailure counter (INCR)300s (5 min)
circuit:open:swiggy:food"1" (open flag)1800s (30 min)
circuit:fail:swiggy:imsame for Instamart300s
circuit:fail:swiggy:dineoutsame for Dineout300s

There's also a health endpoint: GET /api/v1/health/circuits returns current circuit state for all three endpoints.

The Connector Pattern

📄base_connector.py 📄swiggy_connector.py 📄connector_repository.py ✅ Done

The connector pattern is the architectural backbone of all external integrations. Every platform (Swiggy, Zomato, Square POS, EazyDiner) implements the same two-mode interface:

base_connector.py — the contractpython
class BaseConnector(ABC):
    def __init__(self, client: SwiggyMCPClient, db: Session, org_id: int): ...

    async def sync(self) -> dict:
        """
        NIGHTLY JOB. Pulls historical data. Writes to PostgreSQL (Layer 0).
        Think: "download your history into our DB"
        Returns {"synced": N, "errors": M}
        """

    async def enrich(self, context: dict) -> dict | None:
        """
        AT PLANNING TIME. Fetches live signals. Does NOT write to DB.
        Returns enrichment dict, or None on any failure.
        Think: "what's happening on Swiggy right now for this planning run"
        """

sync() vs enrich() — the key distinction

sync()enrich()
WhenNightly / on-demand via APIDuring each planning run
Writes to DB?Yes — PostgreSQLNever — LangGraph state only
Survives restart?Yes — permanentNo — 30 min Redis cache
Data typeHistorical (past orders, bookings)Live signals (prices right now, occupancy tonight)
Status✅ Working (orders + feedback)📋 Coming (P6-S07 to S09)

connector_repository.py

CRUD for the connectors DB table. The table stores per-org platform tokens and sync health. Key methods:

  • get(org_id, "swiggy") — fetch connector row
  • upsert(org_id, "swiggy", **kwargs) — create or update
  • update_sync_status(org_id, "swiggy", "syncing"/"success"/"error")
  • update_token(org_id, "swiggy", token, expires_at)
🏗️
In production: each restaurant owner has their own connector row with their own encrypted Swiggy token. Right now in dev, SWIGGY_ACCESS_TOKEN in .env is used directly (single org). The connector table is ready for multi-tenant from day one.

Order Sync — P6-S03

📄apps/api/app/infrastructure/swiggy/sync/order_sync.py ✅ Done

The first real Swiggy tool call we built. Pulls your last 20 Swiggy delivery orders and writes them to the orders table so the Prophet demand forecaster trains on real delivery demand instead of synthetic data.

The flow

Input: address_id = "cjpfcd75ofl5oefqs8mg" call_tool("get_food_orders", {addressId, orderCount: 20}) → structuredContent: { "orders": [ ... up to 20 orders ... ] } For each order: orderId = "SW-001" items = [{name: "Margherita Pizza", quantity: 2, price: 150}, ...] For each item (idx 0, 1, 2...): ext_id = "SW-001_0", "SW-001_1" ← dedup key Already in DB? → skip (idempotent) Find MenuItem by name (case-insensitive) Not found? → create placeholder MenuItem category="swiggy_import", is_available=False INSERT Order: menu_item_id = found/created item quantity, total_price, ordered_at (parsed from ISO-8601 to UTC) is_delivery = True source = "swiggy" channel = "delivery" external_order_id = "SW-001_0" Returns: {"synced": 5, "skipped": 2, "errors": 0}

Why one row per item?

The existing orders table model links each Order to a specific MenuItem. Swiggy orders have multiple items per order. So a Swiggy order with 3 items = 3 Order rows, each with external_order_id = "SW-001_0", "SW-001_1", "SW-001_2". This matches the DB's cardinality and preserves full item-level detail for Prophet.

Effect on the pipeline

Once enough Swiggy orders are synced, ForecastService can train Prophet specifically on delivery-channel demand. The source="swiggy" and channel="delivery" columns enable filtering so delivery and dine-in demand are forecasted separately.

Feedback Sync — P6-S06

📄apps/api/app/infrastructure/swiggy/sync/feedback_sync.py ✅ Done

This fills in the delivery performance picture. We already have your orders in the DB — now we go back to Swiggy and ask "how did the actual delivery go?" for each one. The result: real delivery latency data in the feedback table, which the complaint_intelligence node uses.

The flow — two tool calls per order

Step 1: call_tool("get_food_orders", {addressId, orderCount: 20}) → gets recent orders For each order: status == "delivered"? → process (pending/out_for_delivery → skip) external_order_id already in feedback table? → skip (dedup) sleep 0.5s ← rate limit courtesy between track calls Step 2: call_tool("track_food_order", {orderId: "SW-001"}) → structuredContent: { deliveryTime: 34, # actual minutes promisedTime: 30, # promised minutes isLate: true # Swiggy's own flag } Handle gracefully: track_raw may be None → skip sentiment, use defaults INSERT Feedback: source = FeedbackSource.swiggy_delivery delivery_time_actual_mins = 34 delivery_time_promised_mins = 30 was_late = True sentiment = SentimentType.negative (isLate=True → negative) SentimentType.positive (isLate=False → positive) raw_text = "Swiggy delivery for order SW-001: 34 min actual vs 30 min promised. Late." external_order_id = "SW-001" # dedup key order_id = (FK to matching Order row, or NULL if not found) Returns: {"synced": 3, "skipped": 2, "errors": 0}

Why 0.5s sleep?

Swiggy's rate limit (even in v1) is 120 req/min per server. We're calling track_food_order once per delivered order. With 20 orders, that's 20 + 1 calls in quick succession. The 0.5s sleep keeps us well under the limit and is courteous to the upstream API.

Effect on the pipeline

The complaint_intelligence node now has real delivery latency patterns to reason about. Instead of "3 customers complained this week (synthetic)", it can say "67% of deliveries were late last week, average delay was 8 minutes".

Reservation Sync — P6-S05

📄apps/api/app/infrastructure/swiggy/sync/reservation_sync.py ⏳ Skeleton

This syncs Dineout table bookings into the reservations table. The tool is get_booking_status(orderId). Simple enough — but there's a chicken-and-egg problem.

🐣
The chicken-and-egg problem: To sync a booking's status, we need its orderId. But orderId is only returned by book_table. And book_table is only built in P6-S16. So right now, sync() has no order IDs to look up — it returns a polite note explaining why.

What's built and ready

register_booking_order_id(org_id, "DO-001") → stores orderId in connectors.connector_metadata JSONB → { "dineout_order_ids": ["DO-001", "DO-002"] } → idempotent (won't add duplicates) Called by: DineoutExecutor (P6-S16) after every successful book_table sync(org_id) → reads connector_metadata["dineout_order_ids"] → empty? return {"synced": 0, "note": "No bookings registered yet..."} → for each orderId: call get_booking_status → INSERT Reservation

Why build the skeleton now?

Because it means P6-S16 (DineoutExecutor) only needs to call register_booking_order_id() — the sync logic is already waiting. The connector_metadata JSONB column on the connectors table was added in migration d2c8f1e4b7a9 specifically for this.

Enrichers — What's Coming Next

P6-S07, P6-S08, P6-S09 · The live market intelligence layer.

Enrichers are fundamentally different from sync services. They don't write to the DB. They run at planning time (when you trigger a scenario) and inject live market intelligence directly into agent prompts.

Chapter 18

Action Layer — P6-S14 to S16

Layer 2 — execution with owner approval gates.

This is where CortexKitchen stops just advising and starts acting. After a planning run identifies a shortage, instead of just saying "you're running low on tomatoes", the system can actually place the Instamart order — but only after the restaurant owner approves.

Instamart procurement flow (P6-S15): ProcurementEnricher found: tomatoes at ₹45/kg, spinId=spin_42 Plan says: "shortage — recommend ordering 10kg" → Action queued: APPROVE_REQUIRED → Owner sees in UI: "Order 10kg tomatoes from Instamart for ₹450. Approve?" → Owner approves → LangGraph interrupt() releases → ProcurementExecutor: update_cart([{spinId: "spin_42", quantity: 10}]) get_cart() → verify ₹450 checkout(addressId) → order placed → procurement_orders table updated Dineout booking flow (P6-S16): OccupancyEnricher: area HIGH tonight, our slots low Plan says: "open 3 more Dineout slots for dinner" → Owner approves → DineoutExecutor: get_available_slots() → find free slot book_table(slotId, itemId, reservationTime, guestCount, lat, lng) On 5xx: get_booking_status before retry (NOT idempotent) → reservations table updated → register_booking_order_id() called (feeds reservation_sync)
🔐
Why the approval gate? checkout and book_table are not idempotent — a double-trigger = double order/booking = real money spent. The LangGraph interrupt() mechanism pauses execution, waits for explicit owner approval, then resumes. This is non-negotiable for any write operation.
