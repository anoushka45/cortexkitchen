Chapter 00

Philosophy — Layering, Not Replacing

The foundational principle behind every decision in the Swiggy integration.

From the first line of Swiggy integration code, one architectural decision was made and never revisited: Swiggy data layers on top of the existing system — it never replaces anything.

The Layering Model

The existing pipeline — with its restaurant operational data, 9-node LangGraph graph, Prophet forecaster, and Qdrant RAG — is the foundation. It works today without any Swiggy token, and it will always work without one.

Every Swiggy integration point adds a new signal to that foundation. Real Swiggy delivery history layers into the orders table alongside the restaurant's own internal records. Live competitor prices inject into agent prompts at planning time. Instamart procurement options appear alongside existing inventory analysis. The agents get smarter — but they never depend exclusively on Swiggy being available.

If Swiggy is unreachable, the system runs on what it has. If Swiggy is connected, every layer of intelligence is amplified by real platform data.

How the data model enables this

Every table that receives Swiggy data has a source column. Rows with source = "internal" are the restaurant's own operational data — their existing orders, POS imports, or records built up within CortexKitchen. Rows with source = "swiggy" are layered on top as the Swiggy connection syncs. Both coexist in the same tables and are queried together — no preference for either, no data gets overwritten.

orders table — both layers coexistsql
-- Restaurant internal data (own records, POS imports, historical data)
SELECT * FROM orders WHERE source = 'internal';   -- seeded at startup

-- Real Swiggy rows (accumulate with each nightly sync)
SELECT * FROM orders WHERE source = 'swiggy';    -- grows over time

-- ForecastService queries ALL rows — no source filter
-- Prophet trains on the combined dataset
-- As Swiggy orders accumulate, the forecast becomes progressively more accurate
SELECT * FROM orders WHERE ordered_at >= :start;  -- this is the actual query

Why internal data stays as the permanent foundation

  • Circuit breaker fallback. When Swiggy is down (3 failures trigger a 30-min block), the pipeline runs on all the restaurant's own operational data already in the DB. Zero degradation.
  • Development without a token. Any engineer can run the full 9-node pipeline locally without a live Swiggy OAuth token. The internal data layer makes this possible at all times.
  • Restaurant onboarding bootstrap. A restaurant that just signed up has zero order history. Their own operational data — imported from POS, entered manually, or built up over time — gives them a meaningful first planning run the moment they connect Swiggy.

The three data layers

LAYER 0 — PostgreSQL (permanent, source-tagged) orders source = internal | swiggy ← pipeline queries all rows feedback source = internal | swiggy_delivery ← complaint_intel uses both reservations source = internal | dineout ← skeleton ready, writes on P6-S16 LAYER 1 — Redis (30 min TTL, live signals injected at planning time) competitor_pricing ← CompetitorEnricher → menu_intel prompt P6-S07 area_occupancy ← OccupancyEnricher → reservation prompt P6-S08 ingredient_market ← ProcurementEnricher → inventory prompt P6-S09 No internal-data fallback for Layer 1. Chapter 02

The Protocol — JSON-RPC 2.0

MCP uses JSON-RPC 2.0. Every Swiggy tool call follows the same envelope.

MCP (Model Context Protocol) is an open standard — created by Anthropic — for how AI agents communicate with external tool servers. Swiggy adopted it. Under the hood it uses JSON-RPC 2.0, a lightweight protocol where every call looks identical. Only the tool name and its arguments change.

Request shape — always the same structure

Any Swiggy tool call — HTTP POSThttp
POST https://mcp.swiggy.com/food
Authorization: Bearer {YOUR_5_DAY_TOKEN}
Content-Type: application/json
Accept: application/json, text/event-stream   ← required — server returns 406 without this

{
  "jsonrpc": "2.0",
  "method":  "tools/call",      ← always this, never changes
  "params": {
    "name":      "get_food_orders", ← changes per tool
    "arguments": {
      "addressId":  "cjpfcd75ofl5oefqs8mg",
      "orderCount": 20
    }
  },
  "id": 1
}
!
Critical discovery — real vs documented format. Swiggy's docs showed {"success": true, "data": {...}}. The actual live server returns JSON-RPC 2.0 format. We discovered this when we used a real OAuth token in P6-S06. All parsing in client.py was updated at that point.

Response shape — what actually comes back

Swiggy response — successjson
{
  "result": {
    "content": [{ "type": "text", "text": "Human-readable summary..." }],
    "structuredContent": { "orders": [...] }   ← this is the data we use
  },
  "jsonrpc": "2.0",
  "id": 1
}

-- Error response:
{ "error": { "code": -32601, "message": "Tool not found" }, "jsonrpc": "2.0", "id": 1 }

call_tool() extracts result["structuredContent"] and returns it directly. Sync services and enrichers receive a plain dict — the JSON-RPC envelope is never visible to them. On any failure, call_tool() returns None.

Chapter 03

OAuth 2.1 + PKCE — Getting the Token

scripts/get_swiggy_token.py · Run once every 5 days.

Before calling any Swiggy tool, we need a Bearer token proving the request comes from an authenticated Swiggy user. Swiggy uses OAuth 2.1 with PKCE (Proof Key for Code Exchange) — a secure flow where a random secret is hashed locally and only the hash travels to Swiggy until the final token exchange.

The full flow — what the script does

1. PKCE setup code_verifier = secrets.token_urlsafe(32) ← random secret, stays local code_challenge = base64url(sha256(code_verifier)) ← hash — safe to send publicly 2. Start local HTTP server on localhost:8080 Background thread · waits for Swiggy's redirect callback 3. Open browser to Swiggy's authorize URL https://mcp.swiggy.com/auth/authorize ?response_type=code &client_id=swiggy-mcp &redirect_uri=http://localhost:8080/callback &code_challenge=HASHED_SECRET &code_challenge_method=S256 4. You log in — phone number + OTP in the browser 5. Swiggy redirects back GET localhost:8080/callback?code=AUTH_CODE Local server catches it, shuts down 6. Exchange code for token POST /auth/token { code, code_verifier, client_id, redirect_uri } 7. Saved automatically to apps/api/.env SWIGGY_ACCESS_TOKEN = eyJ... SWIGGY_ADDRESS_ID = cjpfcd75ofl5oefqs8mg
✓
Confirmed working address ID: cjpfcd75ofl5oefqs8mg — required for all Food and Instamart calls. Dineout uses a separate location system via get_saved_locations.

Chapter 07

SwiggyMCPClient — The Foundation

apps/api/app/infrastructure/swiggy/client.py Live

Every Swiggy tool call in the entire system goes through this class. Its contract: it never raises. Every failure — network timeout, expired token, JSON-RPC error — returns None. Callers never need try/except.

client.py — call_tool() flowpython
async def call_tool(self, endpoint, tool_name, arguments) -> dict | None:
    # 1. Circuit breaker check
    if await is_open("swiggy", endpoint): return None

    # 2. Headers — both are required
    headers = {
        "Authorization": f"Bearer {token}",
        "Content-Type":  "application/json",
        "Accept":        "application/json, text/event-stream",
    }

    # 3. POST and parse response
    result = await self._post(endpoint, payload, headers)

    # 4. Update circuit breaker based on outcome
    await (record_failure if result is None else record_success)("swiggy", endpoint)

    return result   # structuredContent dict, or None on any failure

# _post() handles each failure case and returns None for all of them:
# 401 → token expired | 406 → Accept header (shouldn't happen)
# 5xx → retry once after 1s | "error" key → JSON-RPC error
# result.structuredContent → return it   ← primary path
# result.content[0].text  → {"text": ...} ← fallback

Chapter 08

Circuit Breaker

apps/api/app/infrastructure/swiggy/circuit_breaker.py Live

Without a circuit breaker, a Swiggy outage would cause every planning run to hang for 30 seconds per tool call. The circuit breaker stops calls to a degraded endpoint automatically after 3 failures, giving Swiggy 30 minutes to recover.

CLOSED — normal operation All calls proceed. Failures counted in Redis (5 min sliding window). 3 failures within 5 min → OPEN — endpoint blocked call_tool() returns None immediately. No HTTP request made. Redis key: circuit:open:swiggy:{food|im|dineout} · TTL 30 min Auto-resets when TTL expires. FAIL-OPEN — if Redis itself is down is_open() returns False — calls proceed. System availability > strict enforcement.
Redis KeyPurposeTTL

Chapter 10

Order Sync — P6-S03

apps/api/app/infrastructure/swiggy/sync/order_sync.py Live

Syncs Swiggy delivery order history into the existing orders table as source="swiggy" rows. They sit alongside the restaurant's own internal records in the same table. ForecastService queries all rows without filtering by source — as real Swiggy orders accumulate, they progressively shape the demand forecast.

call_tool("get_food_orders", {addressId, orderCount: 20}) → { "orders": [ {orderId: "SW-001", items: [...], orderedAt: "..."}, ... ] } For each order, for each item at index i: ext_id = "SW-001_i" ← dedup key, sync is idempotent Already in DB? → skip Find MenuItem by name (ILIKE match) Not found? → create placeholder MenuItem (category="swiggy_import") INSERT Order row: source = "swiggy" channel = "delivery" external_order_id = "SW-001_0" ordered_at = UTC datetime ← restaurant's own records untouched, both coexist in same table Returns: {"synced": 5, "skipped": 2, "errors": 0}

Why one DB row per item?

The Order model links each row to a single MenuItem. A Swiggy order with 3 items becomes 3 rows with suffixes _0, _1, _2. This matches the table's cardinality and preserves full item-level detail for Prophet.

Chapter 15

Enrichers — P6-S07, S08, S09

Live market intelligence at planning time. No DB writes. 30-min Redis cache. Next up

Enrichers are Layer 1. They don't touch the DB — they fetch live Swiggy data during a planning run and inject it into agent prompts as context sections. If an enricher fails or Swiggy is unreachable, None is returned and that prompt section is simply absent. The agents still run, drawing from Layer 0 (the DB). No fallback data is needed.
